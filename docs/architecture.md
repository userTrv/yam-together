# Архитектура синхронизации

**Когда пригодится:** чтобы понять, почему у всех играет одно и то же, что будет в тоннеле и где границы точности.

## Главная идея: договариваемся о времени, а не стримим звук

Стримить один аудиопоток всем — дорого, ломается на плохой сети и юридически означает, что мы распространяем музыку. Вагон делает по-другому:

1. Сервер хранит очередь и **якорь**: `{ index, startAt }` — трек номер `index` начал (или начнёт) звучать в момент `startAt` по серверным часам.
2. Конец трека N — это начало трека N+1 через `GAP_MS` (1,2 с на смену источника). Поэтому по одному якорю любой знает, что играет в любой момент: функция `resolve()` в `shared/timeline.js`.
3. Каждый клиент сам получает звук (свой аккаунт, свой файл) и сам выставляет позицию по общим часам.

Любая команда (старт, пропуск, перемотка, продолжение после паузы) ставит новый якорь с запасом `LEAD_MS` = 1,5 с в будущее: все успевают получить событие и подготовить звук, поэтому стартуют вместе, а не «кто первый получил».

## Часы

`public/js/clock.js` делает 5–6 запросов `GET /api/time`, для каждого считает задержку туда-обратно и смещение `serverNow − (t0 + t1)/2`. Берётся медиана смещений по пяти самым быстрым замерам из окна последних 24. Сверка повторяется каждые 30 секунд, при возврате на вкладку и при появлении сети. Погрешность ограничена половиной RTT самого быстрого замера: на 4G обычно 5–30 мс.

## Плеер

`public/js/player.js`, тик каждые 250 мс:

| Расхождение | Действие |
| --- | --- |
| больше 400 мс | перемотка на расчётную позицию плюс оценка времени перемотки (подстраивается сама) |
| 25–400 мс | `playbackRate` в пределах 0,94–1,06, убирает расхождение примерно за 2 с, на слух незаметно (pitch сохраняется) |
| меньше 25 мс | обычная скорость |

Плюс сдвиг под Bluetooth: пользователь задаёт задержку наушников, плеер играет на столько же раньше.

Статусы участников (`synced`, `catching`, `loading`, `unavailable`, `blocked`, `muted`) с расхождением в мс уходят на сервер раз в 5 секунд и рассылаются пачкой раз в секунду. Отсюда строка «В синхроне с 3 пассажирами · разброс 24 мс».

## Метро: что происходит без сети

- Текущий и следующий треки скачиваются целиком в `Blob`, пока есть связь.
- Очередь и якорь у клиента уже есть, часы сверены. Без сети клиент продолжает `resolve()` по локальным часам и сам переключает трек.
- Команды, отправленные без сети, не уходят: интерфейс честно пишет «Нет связи, команда не ушла».
- SSE (`EventSource`) переподключается сам, при подключении сервер присылает полный снимок вагона. Если кто-то за это время нажал паузу, клиент догонит состояние на станции.
- Дрейф кварца телефона за 2 минуты тоннеля — единицы миллисекунд, его съедает плавная подстройка.

## Транспорт

Без WebSocket: события сервер → клиент идут через SSE, команды клиент → сервер обычными POST. Так проще проходить через прокси и мобильные сети, `EventSource` сам переподключается, а зависимостей у сервера ноль.

## Источники звука

- **Демо** (`public/js/synth.js`): трек синтезируется `OfflineAudioContext` из seed. Рендер идёт фразами по 4 такта и склеивается: так узлов в каждом рендере мало, трек на 2 минуты собирается за ~0,5 с. Один seed даёт одинаковую музыку на всех устройствах. Нужны для демо без аккаунта, тестов и офлайна.
- **Яндекс Музыка** (`server/yandex.js`): поиск, `GET /tracks/{id}/download-info`, затем XML с `host/path/ts/s` и подпись `md5(salt + path[1:] + s)`. Каждый получает ссылку своим токеном. Если хранилище не отдаёт файл браузеру напрямую (CORS), его пропускает сервер Вагона, только с хостов `*.yandex.net` / `*.yandex.ru`.

## Безопасность

- Ключ участника вагона выдаётся сервером, сравнивается за постоянное время и не попадает в снимки и события.
- Токен Яндекса только в `localStorage` участника и в заголовке `X-YM-Token`, не логируется и не хранится.
- Аудиопрокси открывает только https-ссылки на хранилище Яндекса, без логина в URL, редиректы перепроверяются.
- CSP `script-src 'self'`, лимиты запросов по IP, ограничения на длину строк и размер тела.

## Что не сделано и куда расти

- Состояние в памяти одного процесса. Для масштаба — Redis или Postgres для вагонов и pub/sub для событий.
- Нет собственного приложения: фоновое воспроизведение на iOS в браузере работает, но системный плеер управляет только своим треком. Нативная оболочка решит.
- Точность ограничена `<audio>`: для десятков миллисекунд хватает, для «тихой дискотеки» с колонками нужен Web Audio с измерением `outputLatency`.
- Официальная интеграция с Яндекс Музыкой: см. [pitch-yandex.md](pitch-yandex.md).
